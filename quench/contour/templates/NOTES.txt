Confirm the controller is really reconciling -- not merely Ready -- by giving it an
HTTPProxy and reading back the status it writes:

  kubectl -n {{ .Release.Namespace }} apply -f - <<'EOF'
  apiVersion: projectcontour.io/v1
  kind: HTTPProxy
  metadata:
    name: example
  spec:
    virtualhost:
      fqdn: example.local
    routes:
      - conditions: [{prefix: /}]
        services:
          - name: my-app
            port: 80
  EOF
  kubectl -n {{ .Release.Namespace }} get httpproxy example -o jsonpath='{.status.currentStatus} {.status.description}'

A "valid" status means Contour parsed the object and programmed it. "invalid" with a
description naming a missing Service means Contour is working and your backend is not.

The Contour<->Envoy xDS mTLS keypairs were minted in-cluster by a `contour certgen` hook
Job into Secrets {{ include "contour.contourCertSecretName" . }} and {{ include "contour.envoyCertSecretName" . }}.
They are valid for {{ .Values.xdsTLS.certgen.certificateLifetime }} days and are NOT owned by this Helm release, so
`helm uninstall` leaves them behind. The hook does not overwrite them, so upgrades are a
no-op; rotating means minting a new CA AND restarting both workloads, because a running
Envoy keeps trusting the retired one:

  helm upgrade ... --set xdsTLS.certgen.overwrite=true
  kubectl -n {{ .Release.Namespace }} rollout restart deployment/{{ include "quench-common.fullname" . }}{{ if .Values.envoy.enabled }} daemonset/{{ include "contour.envoyName" . }}{{ end }}
{{- end }}

The CRDs (HTTPProxy, ContourConfiguration, ExtensionService, TLSCertificateDelegation)
were installed from crds/. Helm never upgrades or deletes files in crds/, so a Contour
upgrade that changes a CRD schema needs them applied by hand.

The images are pinned by digest and signed. Verify them:

  cosign verify ghcr.io/quenchworks/images/contour \
    --certificate-identity-regexp 'https://github.com/quenchworks/.+' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com
