Quenchworks Crossplane is installed as {{ include "quench-common.fullname" . }}.

The control plane runs nonroot with a read-only root filesystem. Its core CRDs were
installed by the `init` container from /crds INSIDE the image, so CRDs and controller are
always at the same revision -- there is no crds/ directory in this chart to drift.

{{- if .Values.core.webhooks.enabled }}
  webhooks:   {{ include "quench-common.fullname" . }}.{{ .Release.Namespace }}.svc:{{ .Values.service.port }} (TLS from {{ include "crossplane.tlsCASecret" . }})

{{- else }}
  rbac mgr:   DISABLED -- installed Providers will NOT be granted the permissions they

Confirm the control plane is up and owns its APIs:

  kubectl get deploy -n {{ .Release.Namespace }} -l app.kubernetes.io/instance={{ .Release.Name }}
  kubectl get crd -l app.kubernetes.io/part-of=crossplane
  kubectl api-resources --api-group=pkg.crossplane.io

Install a Provider (fully qualified references only -- Crossplane has no default registry):

  kubectl apply -f - <<'EOF'
  apiVersion: pkg.crossplane.io/v1
  kind: Provider
  metadata:
    name: provider-nop
  spec:
    package: xpkg.crossplane.io/crossplane-contrib/provider-nop:v0.4.0
  EOF

  kubectl get provider.pkg -w      # wait for INSTALLED=True HEALTHY=True

Then define your own API with a CompositeResourceDefinition and a Composition; see
https://docs.crossplane.io/latest/getting-started/.

Hand out access with the aggregated roles the RBAC manager fills in per XRD:

  {{ include "crossplane.clusterRoleName" . }}-admin / -edit / -view / -browse

They are EMPTY until your first XRD exists. Members of the group
{{ include "quench-common.fullname" . }}:masters already have the -admin role bound.

One Crossplane per cluster. Its CRDs, the aggregation labels the RBAC manager writes, and
the webhook configurations it registers are all cluster-scoped and not namespaced by
release, so a second release would fight the first.
